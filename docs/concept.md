# AI 时代的图形化项目管理 · 概念设计

> 配套图形版：[concept.html](concept.html)（以图为主，本文为文字底稿）

## 1. 问题

AI（Claude Code / Codex）的编码能力越来越强，单个人能推动的项目规模越来越大；但人的注意力和记忆没有变。

传统做法是把项目拆成 N 个步骤、N 个任务，用列表和看板管理。项目一旦大到几十上百个模块，列表就失效了：

- **看不见全局**：列表是线性的，项目却是立体的（物理部署、逻辑分层、功能模块）。
- **"做了"不等于"有用"**：B 做完了，但它依赖的 A 没做，B 的价值根本发挥不出来，列表上却显示"已完成"。
- **不知道下一步做什么**：任务太多，开发者无法判断哪件事对目标的推动最大。

## 2. 核心主张

| 传统管理 | 本方案 |
|---|---|
| 用列表/文字描述进度 | 在**架构图**上直接着色，一眼看懂 |
| 只问"做没做" | 区分 **已建成** 与 **已生效** |
| 按任务排期 | 从**目标**倒推缺口，按**杠杆**排序下一步 |

### 关键概念：模块的四种状态

| 状态 | 含义 |
|---|---|
| ⚪ 未建 | 没有验收测试，或尚无任何实现 |
| 🔵 进行中 | 有验收测试，但尚未全部通过（代码再多也只算进行中） |
| 🟠 已建未生效 | 自身验收测试通过（上游用替身隔离），但依赖的上游未生效，价值被阻塞 |
| 🟢 已生效 | 自身验收通过，且所有硬依赖都已生效 |

**完成的判定标准是"成果"而不是"成本"**：一个模块算"已完成"，唯一依据是它的验收测试通过；写了多少代码、花了多少时间都不算。

**生效规则（递归）**：`生效(X) = 已完成(X) 且 X 的所有硬依赖均已生效 且 X 的跨视图支撑节点均已生效`（跨视图部分见决策 4）。生效状态本身也可以用端到端测试（接真实上游）来交叉验证。

由此得到两个指标：

- **建成度** = 已完成模块数 / 总模块数（传统进度）
- **生效度** = 已生效模块数 / 总模块数（真实可用程度）

两者之间的差值，就是"做了但白做（暂时）"的部分——这是传统看板看不见的风险。

## 3. 五个视图

### 视图一：架构地图（看全局）

- 以项目的架构图为底图，支持三种切换：**物理架构**（部署、服务器、存储）、**逻辑架构**（分层、服务边界）、**功能模块**（用户可感知的能力）。
- 每个模块按四种状态着色；切换"建成视角 / 生效视角"可以立刻看出被阻塞的区域。
- 不出现任务列表。

### 视图二：效用关系图（看依赖）

- 模块之间画出依赖边（硬依赖 / 软依赖）。
- 点击任一模块：高亮它的上游依赖链和下游影响面，并指出**根因阻塞点**（链路上真正没做的那个模块）。
- 阻塞沿依赖边向下游"传播"，用红色虚线表示断链。

### 视图三：目标缺口（看下一步）

- 每个目标（G1、G2、G3…）声明它需要哪些终端能力；系统自动展开其依赖闭包。
- 对每个目标显示：生效进度环、**还缺哪些模块要建**、**哪些已建但被阻塞**。
- **下一步推荐**：按"完成它能解锁多少下游模块、推进哪些目标"排序，并给出 what-if 预估（"做完 A、B 后，G1 从 45% 升到 91%"）。

### 视图四：成本（看投入）

成本不算进度（决策 2），但它回答另一个问题：**投入花在了哪里，值不值**。两个维度：

- **时间**：模块从开工（验收条目锁定）到现在、或到完成，一共多久。
- **Token**：AI 在这个模块上一共消耗了多少 token。

展示方式：以"时间 × token"为坐标的气泡图，气泡颜色是模块的生效状态。重点看两类信号：

- **沉没风险**：大量 token 花在"已建未生效"的模块上——钱花了，价值还没兑现。
- **卡住预警**：长时间处于"进行中"、token 还在持续增长的模块——可能拆错了，或者 AI 在原地打转。

### 视图五：旅程蓝图（看用户能走多远）

前四个视图按结构或数字组织，唯独缺了**时间**这个维度：目标在用户眼里是一段旅程。视图五借鉴服务设计里的三种图表：

- **服务蓝图（Service Blueprint）作骨架**：横向是旅程步骤，纵向是泳道，正好对上三套架构——

  | 蓝图泳道 | 对应 |
  |---|---|
  | 用户行为 | 功能视图（旅程步骤） |
  | 前台 | 逻辑视图·前端层 |
  | 后台 | 逻辑视图·服务层 |
  | 支撑系统 | 数据层、外部依赖、物理视图 |

  泳道之间保留蓝图的三条线：交互线、**可见线**、内部交互线。"已建未生效"在蓝图上的含义是：问题出在可见线以下，用户看不到原因，只会发现这一步走不通。跨视图阻塞（决策 4）表现为同一列里从下往上断掉的一条红线。

- **旅程地图（Journey Map）的情绪曲线 → 可用性曲线**：每一步是"可用 / 断开 / 映射缺口"，一眼看出用户走到第几步会断。
- **故事地图（Story Map）的切线**：旅程步骤可以标 `slice: later`，表示不在当前目标范围内；"下一步推荐"只为切线以上的步骤服务。

**蓝图不手画，由引擎推出来**：人只声明旅程步骤对应哪个功能节点；每列的泳道内容 = 实现该功能的组件及其上游依赖闭包，按所在层分到前台 / 后台 / 支撑。

**顺带检查映射缺口**：某一步找不到实现它的组件，泳道就是空的——要么映射漏了，要么那一块根本还没设计。

一步"可用"的判定：该列所有节点都已生效。

## 4. 示例项目：智能知识库问答平台

13 个模块，分四层：

- 前端层：登录页 ✅、对话界面 ✅、知识库管理台 🔵、数据看板 ⚪
- 服务层：用户认证 ✅、对话服务 ✅、向量检索 ⚪、文档解析 ✅、计费服务 ⚪
- 数据层：用户库 ✅、向量数据库 ⚪、对象存储 ✅
- 外部：LLM 网关 ✅

**建成度 62%（8/13），生效度只有 38%（5/13）。** 对话界面、对话服务、文档解析三个模块已写完，却因为"向量数据库 → 向量检索"没做而全部无法生效。

| 目标 | 生效进度 | 待建 | 已建但被阻塞 |
|---|---|---|---|
| G1 用户能基于自有文档提问并得到答案 | 45% | 向量数据库、向量检索、知识库管理台 | 对话界面、对话服务、文档解析 |
| G2 用户能安全登录与管理账号 | 100% | — | — |
| G3 平台可按用量计费 | 33% | 计费服务、数据看板 | — |

**推荐下一步**：先做 向量数据库 → 向量检索。完成后 3 个已写好的模块立即生效，G1 从 45% 跃升至 91%。

**旅程蓝图**：G1 的旅程"登录 → 上传文档 → 提问 → 查看引用"中，只有"登录"可用；"上传文档"断在知识库管理台（进行中）和向量检索、向量数据库（未建）；"提问"断在可见线以下的向量检索链路；"查看引用"在切线以下，而且没有任何实现组件，被标为映射缺口。

**成本视角**：项目累计消耗约 245 万 token，其中 **193 万（79%）花在尚未生效的模块上**（对话界面、对话服务、文档解析、知识库管理台）。知识库管理台已进行 6 天、消耗 61 万 token 仍未通过验收，触发卡住预警。

## 5. 运作机制（如何与 AI 编码结合）

1. **项目模型文件**：仓库根目录放一份 `pm.yaml`，描述模块、所属层、依赖、目标。可由 AI 首次扫描代码生成，人只做校对。
2. **状态由测试结果决定**：每个模块在 `pm.yaml` 里绑定自己的验收测试。AI 每次会话结束后（Claude Code hook / skill）运行这些测试，按结果更新状态；不看代码有没有写、写了多少，也不靠人手填。
3. **计算引擎**：根据依赖图计算生效状态、根因阻塞、目标缺口与杠杆排序。
4. **渲染五视图**：输出单文件 HTML，本地打开即看；也可作为 Claude Code 侧边面板实时刷新。
5. **反哺 AI**：把"下一步推荐"作为上下文喂回给 AI，让 AI 也知道当前最该做什么。

### `pm.yaml` 草案

```yaml
project: 智能知识库问答平台

# 三套架构各自独立建模，节点不要求一一对应；每个视图 ≤ 40 个节点
views:
  functional:              # 功能架构：用户可感知的能力
    - id: f-ask-doc
      name: 基于文档问答
      acceptance: [tests/acceptance/ask_doc.spec.ts]   # 状态只由这里的测试结果决定
      depends: [{ on: f-upload-doc, kind: hard }]
  logical:                 # 逻辑架构：分层与服务边界
    - id: retrieval
      name: 向量检索
      layer: service
      acceptance: [tests/acceptance/retrieval.test.py]
      depends: [{ on: vector-db, kind: hard }]
    - id: chat-svc
      name: 对话服务
      layer: service
      acceptance: [tests/acceptance/chat_svc.test.py]
      depends: [{ on: retrieval, kind: hard }, { on: llm-gw, kind: hard }]
  physical:                # 物理架构：部署、机器、存储
    - id: pg-vector
      name: PG 向量实例
      acceptance: [ops/healthcheck/pg_vector.sh]

# 跨视图映射：部分、可选；没有映射的节点完全合法
# 一旦建立即为跨视图硬依赖：to 未生效 → from 也不生效（阻塞沿 物理 → 逻辑 → 功能 传播）
mappings:
  - { from: f-ask-doc, to: chat-svc, kind: realized_by }   # 功能 → 逻辑
  - { from: retrieval, to: pg-vector, kind: deployed_on }  # 逻辑 → 物理
  - { from: chat-svc, to: [app-1, app-2], kind: deployed_on, require: any }  # 冗余部署，任一健康即可

# 状态不手写：由引擎运行 acceptance 后得出 todo | doing | done
goals:
  - id: G1
    name: 用户能基于自有文档提问并得到答案
    requires: [login-page, chat-ui, kb-console]
    journey:                    # 视图五：只声明步骤 → 功能节点，泳道由映射自动推出
      - { step: 登录,     functional: f-login }
      - { step: 上传文档, functional: f-upload-doc }
      - { step: 提问,     functional: f-ask-doc }
      - { step: 查看引用, functional: f-cite, slice: later }   # 故事地图切线以下
```

## 6. MVP 路线

1. **P0 数据模型**：定义 `pm.yaml` schema + 生效 / 缺口 / 杠杆 / 成本计算引擎（含单元测试）。
2. **P1 静态渲染**：从 `pm.yaml` 生成单文件 HTML 五视图。
3. **P2 Skill 接入**：项目开始时初始化 `.pm/`；每个功能开工时起草验收条目，会话结束运行验收测试、记录 token、刷新状态。
4. **P3 本地面板**：在 Claude Code 内作为常驻面板，随代码变化实时刷新。
5. **P4 云端与多项目**：账号下自动注册项目，云上查看单项目页面和多项目总览。

## 7. 已确定的设计决策（2026-10-26）

### 决策 1：模块粒度 = 独立可验收的能力

- 一个模块 = 一项能单独验收（单独测试）的能力。拿不出验收标准的东西，说明拆得不对：要么太碎，要么太虚。
- 单个视图不超过 40 个节点；超出时按层级折叠，点开再看下一层。

### 决策 2：状态看成果，不看成本

- "已完成"的唯一依据是验收测试通过。代码行数、提交次数、耗时都属于成本，不作为进度依据。
- 由此得到三层证据：
  - 没有验收测试 → 未建
  - 有测试但未全部通过 → 进行中
  - 自身验收通过 → 已完成；再叠加上游依赖，区分"已建未生效"和"已生效"
- 推论：AI 写了大量代码但测试没过，地图上依然是蓝色"进行中"。这能防止"AI 产出很多、看起来很忙"的进度错觉。

### 决策 3：三套架构各自独立，部分映射

- 物理、逻辑、功能三张图的职责是分别讲清物理、逻辑、功能层面的事，各有自己的节点集合，**不要求同一个模块在三张图里都有对应**。
- 视图之间可以建立映射，但映射是部分的、可选的：
  - 功能 → 逻辑：`realized_by`（某个功能由哪些逻辑组件实现）
  - 逻辑 → 物理：`deployed_on`（某个逻辑组件部署在哪里）
- 映射的用途是"跨视图钻取"：点击一个功能节点，可以跳到实现它的逻辑组件，再跳到它所在的物理节点。没有映射的节点照样有自己的状态和依赖，在本视图内独立计算。

### 决策 4：跨视图阻塞要传播

- **传播方向**：沿映射从"支撑方"传到"被支撑方"——物理 → 逻辑 → 功能。
  - `deployed_on`：逻辑组件部署在某个物理节点上；物理节点未生效（如健康检查失败、尚未部署），该逻辑组件也不生效。
  - `realized_by`：功能由某些逻辑组件实现；任一实现组件未生效，该功能也不生效。
  - 反方向不传播：功能没做完，不会让底下的逻辑组件或物理节点变成"未生效"。
- **完整的生效规则**：
  `生效(X) = 已完成(X) ∧ 本视图所有硬依赖生效 ∧ 所有跨视图支撑节点生效`
  也就是说，映射在计算上等同于一条"跨视图的硬依赖"。
- **多个支撑节点**：默认全部都要生效（AND）。冗余部署的场景（比如部署在两台副本上，有一台健康就行）可以在映射上标 `require: any`。
- **没有映射的节点不受影响**：它们只按本视图的规则计算。这和决策 3 一致：映射是可选的，但一旦建立就是真实的约束。
- **展示**：
  - 因跨视图原因被卡住的节点，额外标一个"跨视图"角标，和本视图内的阻塞区分开。
  - 点击节点时，"根因阻塞"会注明根因在哪个视图（例如"根因在物理视图：PG 向量实例 健康检查失败"），并可一键跳过去。
  - 目标缺口与下一步推荐会把跨视图的根因也算进来，所以推荐的"下一步"可能是一个物理层的动作（比如"把向量实例部署上线"）。
- **校验**：本视图依赖边和跨视图映射合在一起必须无环；引擎载入 `pm.yaml` 时检查，有环直接报错并指出环路。

### 决策 5：验收测试——人定功能层标准，其余交给 AI

- **格式**：验收条目写成 Gherkin `.feature` 文件（Given / When / Then），每个节点 1–5 条，放在 `.pm/acceptance/` 下。
- **分工**：
  - 功能层的验收条目：AI 起草，**人逐条确认**。这是人对"什么算成果"的唯一把关点。
  - 逻辑层、物理层的验收条目：AI 在已确认的功能条目基础上生成，自己确认，人可以抽查。
  - 测试代码与实现代码都由 AI 写；写实现的会话尽量不和写测试的是同一个。
- **锁定与待复核**：
  - 条目确认后，条目和对应测试文件的指纹（hash）记入 `pm.yaml`。
  - 之后测试文件一旦被改动，节点挂上"待复核"标记（不阻断工作），地图上醒目提示；人复核通过后，按新指纹重新锁定。
- **先失败、后通过**：新测试必须先在未实现的代码上跑出失败结果，证明它真的在检验东西。
- **按节点类型选测试**：功能节点用端到端用户流程，逻辑节点用接口契约测试（上游用替身），物理节点用健康检查与部署探针。单元测试不算验收。
- **流程**：人确认目标 → AI 拆模块、起草条目 → 人确认功能层条目 → AI 生成其余条目 → 锁定 → AI 生成测试（失败）→ AI 实现（通过）→ 引擎更新状态。

### 决策 6：成本只展示、不计入进度

- 时间：以验收条目锁定为开工时间，到完成或当前时刻。
- Token：每次 AI 会话开始时声明当前在做哪个模块，会话结束时由 hook 把本次 token 用量记入 `.pm/ledger.jsonl`，按模块汇总。
- 成本视图与进度视图分开展示，避免"花得多 = 做得多"的错觉。

## 8. 遗留问题

- 一次会话同时动了多个模块时，token 怎么分摊？初步方案：按各模块涉及的文件改动量比例分摊。
