Concept · AI-era Project Management

项目被 AI 放大了，
人需要看图管理

不再用列表追踪"做没做"，而是在架构图上直接看到：哪里已生效、哪里被阻塞、离每个目标还差什么、下一步做哪件事杠杆最大。

01

核心概念：做了 ≠ 生效

每个模块有四种状态。一个模块只有在自身完成、且所有硬依赖都已生效时，才真正"生效"。

02

视图一 · 架构地图

示例项目「智能知识库问答平台」。切换视角对比：同一张图，在"建成视角"里一片绿，在"生效视角"里暴露出被阻塞的区域。点击任一模块查看依赖链。

03

视图二 · 阻塞是如何传播的

根因只有两个未建模块，却让三个已经写完的模块全部失效。传统看板会把它们显示为"已完成"。

视图三 · 目标缺口与下一步

从目标倒推：每个目标展开其依赖闭包，显示还缺什么、什么被卡住，并按杠杆给出下一步。

下一步杠杆排序

完成该模块后，下游有多少模块不再被它阻塞

05

视图四 · 成本：投入花在了哪里

决策 6：成本只展示、不计入进度。每个气泡是一个模块，横轴是已投入天数，纵轴是消耗的 token，颜色是生效状态。

07

设计决策 D1–D5

2026-10-26 确定：节点粒度、状态依据、三套架构的关系、跨视图阻塞传播，以及验收测试由谁来写。

D1 · 粒度

一个节点 = 一项可独立验收的能力

拿不出验收标准的，说明拆得不对。单个视图不超过 40 个节点，超出就分层折叠。

D2 · 依据

看成果，不看成本

代码行数、提交次数、耗时都是成本，不算进度。AI 写了几千行但测试没过，依然是"进行中"。

D3 · 视图

三套架构各说各的，部分映射

功能、逻辑、物理各有自己的节点，不要求一一对应。映射是可选的，但一旦建立就是真实约束。

D4 · 跨视图传播

阻塞沿映射向上传导：物理 → 逻辑 → 功能

映射等同于一条跨视图的硬依赖：支撑节点未生效，被支撑节点也不生效；反方向不传播。冗余部署可标 require: any，任一健康即可。本视图依赖与跨视图映射合起来必须无环。

D5 · 验收测试

人只把关"什么算成果"，其余交给 AI

验收条目写成 Gherkin .feature：功能层由人逐条确认，逻辑层与物理层由 AI 在此基础上生成。确认后锁定指纹；测试文件一旦被改动，节点挂"待复核"，不阻断工作，人复核后重新锁定。

08

运作机制：让 AI 维护这张图

人不手填状态。AI 扫描仓库生成项目模型，每次编码会话后运行验收测试、按结果刷新，并把"下一步"反哺给 AI。

09

MVP 路线

P0

数据模型

pm.yaml schema + 生效 / 缺口 / 杠杆 / 成本计算引擎

P1

静态渲染

从 pm.yaml 生成单文件 HTML 五视图

P2

Skill 接入

项目开始时初始化 .pm/，每个功能起草验收条目，会话结束跑测试、记 token

P3

本地面板

Claude Code 内常驻面板，随代码变化实时刷新

P4

云端与多项目

账号下自动注册项目，云上看单项目页与多项目总览
